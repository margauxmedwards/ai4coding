The missing context is operational

“Deploy this on the HPC” leaves the scheduler, queue, environment, storage and definition of success unspecified. A plausible script can still be wrong for your cluster.

Environment

PBS version, allowed queue, resource limits, project directory and working environment.

Data

Input format, absolute paths, small test sample and expected output schema.

Evidence

Job completion status, logs, conversion manifest and sample-level validation.

Authority

Which edits and test jobs are authorised? Does a full run need a separate decision?

A job ID means the scheduler accepted a submission. It does not establish that the job ran or produced correct data.

Confirm site-specific commands and storage policies against Aqua documentation before running a job.

[04] · ADVANCED

Define success at three levels

1 · Code

Relevant tests pass. Existing behaviour is preserved. The diff stays within scope.

2 · Execution

The PBS job finishes successfully. Logs and environment details are recorded.

3 · Data

Validate expected topics, counts, timestamps and a decoded sample against the input.

Task: prepare a PBS job for a small rosbag conversion sample.
Context: read the project instructions, lockfile and cluster docs.
Success: completed job, saved logs, validated output manifest.
Boundaries: no full dataset run, no source deletion, no publishing.
Report: files changed, commands, job status, checks and unknowns.
If blocked: report the cause and preserve evidence; do not guess.
For ROS package tests, an exit-code gate should use colcon test --return-code-on-test-failure. Also inspect the reported tests; a successful build is not a behavioural test.

[05] · ADVANCED

Use checkpoints where decisions matter

For a known local fix, let the agent inspect, edit and verify within the authorised scope. For an expensive or remote workflow, put checkpoints at changes of scope.

Inspect + plan

Read the actual files and documentation. State assumptions, affected paths and checks.

Implement + test

Use a branch or isolated working copy with a saved baseline. First run a small representative sample.

Review + expand

Inspect the diff and evidence. Authorise a full run only when the small run meets its criteria.

Recover + record

Keep failed-run logs and partial-output status. Save the next action so another session can resume.

Ask for plans, commands and evidence that you can review. A long explanation is not a substitute for observed results.

A PBS example with explicit adapters

Teaching template, not a verified Aqua job. Confirm queue, resource limits, environment setup and scratch policy. This version assumes a single-file input bag. ROS2 directory bags need different staging.

#!/usr/bin/env bash
#PBS -N rosbag_sample
#PBS -l select=1:ncpus=4:mem=16gb
#PBS -l walltime=00:20:00
# Add the queue directive verified for your site.
set -euo pipefail
: "${PBS_O_WORKDIR:?missing project directory}"
: "${PBS_JOBID:?missing job id}"
: "${INPUT_BAG:?set an absolute input file path}"
: "${OUTPUT_DIR:?set a new absolute output directory}"
[[ "$INPUT_BAG" = /* && "$OUTPUT_DIR" = /* ]]
[[ -f "$INPUT_BAG" && ! -e "$OUTPUT_DIR" ]]
cd "$PBS_O_WORKDIR"
JOB_ID="${PBS_JOBID%%.*}"
mkdir -p logs/convert-rosbag
exec >"logs/convert-rosbag/${JOB_ID}.out" \
     2>"logs/convert-rosbag/${JOB_ID}.err"

# Site adapter: confirm this variable with cluster docs.
: "${PBS_TMPDIR:?confirm the site scratch location}"
WORK_DIR=$(mktemp -d "${PBS_TMPDIR}/convert.XXXXXX")
cp -- "$INPUT_BAG" "$WORK_DIR/input.bag"

# Project adapter: these tasks must exist in pixi.toml.
pixi run convert-rosbag --input "$WORK_DIR/input.bag" \
  --output "$WORK_DIR/output"
pixi run validate-conversion --input "$WORK_DIR/input.bag" \
  --output "$WORK_DIR/output"

# A partial copy must not be mistaken for a completed run.
mkdir -- "$OUTPUT_DIR"
cp -a -- "$WORK_DIR/output/." "$OUTPUT_DIR/"
printf '%s\n' "$PBS_JOBID" > "$OUTPUT_DIR/COMPLETE"
# Site scratch may be removed when the job ends.
# Plan durable failure logs/checkpoints before a long run.
Before submission: replace the site/project adapters, validate shell syntax and test with a tiny copied input. The COMPLETE marker records successful copy-back after validation; consumers must ignore unmarked output directories.

Unlike an unconditional cleanup trap, this example does not explicitly delete scratch on failure. That still cannot prevent scheduler cleanup: preserve valuable intermediate results on durable storage.

Use the right kind of customisation

MechanismUse it forCheck
InstructionsGeneral or file-scoped conventionsWhich files were actually loaded?
SkillA reusable task procedure with optional scriptsWas it invoked, and do the prerequisites hold?
Custom agentA recurring role with selected toolsDoes it have only the access needed for this task?
HookA command triggered by supported agent lifecycle eventsEvent names and behaviour depend on the tool.
MCP serverExpose tools and data through a common protocolWhich tools are connected and authorised?
PluginPackage capabilities and integrationsSupported host, permissions and dependencies.

The concepts transfer across tools; file locations, activation rules and features do not transfer automatically. MCP does not make every editor extension available to every model.

[10] · ADVANCED

Run a comparison you can trust

  • Choose several representative tasks: a small bug, a multi-file change and a pipeline failure. Define acceptance checks before any model sees them.
  • Start each trial from the same commit, fixtures and task brief. Use separate working copies.
  • For a model comparison, hold the tool, permissions and available context constant. Record exact model names, date and reasoning settings.
  • Give each trial the same time or spend limit and correction policy. Repeat trials when practical; record failures too.
  • Review the diff and independently run the acceptance checks. A second model can propose findings, but reproduce each material finding.
  • Compare successful completion, regressions, human corrections, elapsed time and total cost. Do not select on tokens alone.

[11] · ADVANCED

Budget for a successful outcome

Scope

Ask for the smallest coherent change and focused output. Avoid dumping an entire repository into chat.

Measure

Track actual usage and retries on representative tasks. API token prices and product credits are different billing units.

Stop

Set a bounded trial. After repeated failure, inspect evidence and revise the approach.

Restart deliberately

Write a handoff before opening a fresh session. Include the commit, tests, unresolved work and next command.

A fresh chat can reduce irrelevant history, but it may also need to reload context. Caching, compaction and product billing affect the result; restarting is not guaranteed to cost less.

Handoff
- Goal and agreed scope
- Current commit / branch and uncommitted changes
- Relevant files and documentation versions
- Commands run, results and evidence paths
- Known failure or remaining uncertainty
- Next action and actions not yet authorised
Do not turn one observed credit charge into a universal price per edit. Recheck current plan limits and actual usage for the selected model.

[12] · ADVANCED

Close the loop with verified lessons

Run → inspect evidence → reproduce the failure → improve the procedure → test it again. Save general lessons and keep one-off incident details in the run log.

Keep

A verified command, a real environment constraint or a reliable validation step.

Avoid

A guessed API rule, a workaround that hides failures, or a stale model-specific instruction.

Recheck

Run a small known task after changing a skill, model or tool.

Share

Commit reviewed workflow updates so the team can trace what changed.

Better context makes the task clearer. Verification establishes whether it worked.
