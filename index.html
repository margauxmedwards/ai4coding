[01] · ADVANCED

Turn repeated research work into reusable capability

The beginner talk gets you to one verified edit. This talk asks: what do you keep explaining, checking or rebuilding every week—and how can you make that process easier to repeat?

Notice the repetition

Dataset checks, experiment setup, results tables, figures and paper updates.

Capture the method

Write down inputs, decisions, commands, expected outputs and checks.

Build a small tool

Put stable calculations and mechanical checks into code.

Teach the workflow

Use a skill to guide an agent through the tool, exceptions and evidence.

Running example: turn experiment results into a checked comparison table and a traceable research summary.

[03] · ADVANCED

Write the recipe before building the automation

Walk through one successful example and one failure. Record the decisions you normally make without thinking about them.

Process: compare two methods on a fixed benchmark.
Inputs: results CSV, evaluation protocol, expected run list.
Rules: same dataset version, split, metric and planned seeds.
Steps: validate → aggregate → compare → render → review.
Outputs: validation report, comparison table, source manifest.
Stop when: runs are missing, duplicated or incomparable.
Human decision: whether the evidence supports the research claim.

Make assumptions visible

What is a run? Which direction is better? Are scores fractions or percentages?

Define completion

Specify the output schema and the checks that must pass.

Design failure output

Report the exact missing or incompatible records and the next useful action.

Limit the first version

One input format, one metric and one known comparison are enough to start.

[05] · ADVANCED

Develop the smallest useful research tool

Ask the coding agent to implement one reliable operation before adding a broad workflow. The following is a proposed interface to build in your research repository, not a command shipped with this presentation.

python scripts/compare_runs.py \
  --input results/runs.csv \
  --protocol configs/evaluation.json \
  --output results/comparison-v1/

Explicit contract

Define required columns, metric units, accepted values, run identity and output format.

Useful failures

Exit nonzero for missing seeds, duplicate runs or incompatible protocols. Name the offending records.

Repeatable outputs

Use stable ordering and deterministic calculations. Refuse to overwrite an existing result unless explicitly requested.

Traceable evidence

Save input hashes, code revision, protocol and tool versions, command and validation status alongside the table.

Build a comparison tool for this CSV and protocol.
First inspect the inputs and propose a small interface.
Keep the aggregation rules in code and document them.
Add tiny fixtures with hand-calculated expected results.
Report missing runs; never silently drop or invent them.
Generate a table and provenance manifest from the same inputs.
A command-line script is often enough. Add an API or MCP interface only when a real integration need makes it useful.

Make correctness observable

Use a small fixture you can calculate by hand before processing a real experiment. These numbers are illustrative, not research results.

MethodSeed 1Seed 2Seed 3Mean score
Baseline0.770.790.810.79
Candidate0.800.820.840.82

Expected difference: +0.03 on the 0–1 scale, or +3 percentage points. This toy example establishes the arithmetic, not statistical significance or generalisation.

  • Check the valid fixture against its hand-calculated answer.
  • Remove one expected seed: the tool should report an incomplete comparison.
  • Duplicate a method–seed row: it should fail rather than count the run twice.
  • Change the dataset version, split or metric units: it should reject the comparison.
  • Check that the rendered table matches the machine-readable output and retains the run count.
Choose aggregation and uncertainty methods as part of the research protocol. Do not let an agent choose whichever summary makes the result look strongest.

[07] · ADVANCED

Wrap the verified tool in a skill

Once the tool works, capture the repeated procedure in a skill. Keep detailed schemas and examples in linked files. This illustrative skill assumes the comparison script has been implemented and tested.

# .github/skills/compare-experiments/SKILL.md
---
name: compare-experiments
description: Produce checked comparisons of experiment runs. Use when updating benchmark tables or summarising repeated runs.
---
1. Read [the protocol](references/evaluation-protocol.md).
2. Confirm methods, dataset version, split, metric and seeds.
   Ask if a required choice is missing; do not infer a new protocol.
3. Run scripts/compare_runs.py with explicit input, protocol
   and a new output directory. Follow the tool's --help.
4. If validation fails, report offending records and stop.
   Do not omit failed runs or fabricate missing measurements.
5. Check the table against the summary and provenance manifest.
6. Draft an interpretation citing the output files and limits.
7. Report commands, checks, outputs and unresolved questions.
   Propose workflow improvements for review before saving them.

Use a supported skill location and required frontmatter. Invoke the skill explicitly for its first trial, then check that the agent loaded it and followed the procedure. File locations and activation rules vary by tool.

Source: VS Code skill structure and loading

[08] · ADVANCED

The second run should need less explanation

First run · identify the gap

An experiment table is missing one candidate seed. The validator reports the missing record.

Respond · resolve the evidence

Check whether the run failed, was never executed, or was exported incorrectly. Preserve that distinction.

Improve · save a tested check

If the gap exposed a missing check, add a fixture and update the tool. Add the recovery procedure to the skill.

Next run · use the same recipe

Invoke the skill on a new result file. Confirm that the previous failure is detected without another long explanation.

Use the compare-experiments skill for Baseline and Candidate.
Inputs: results/runs.csv and configs/evaluation.json.
Write a new results/comparison-v2/ directory.
Report the validation outcome and source files for every number.
If data is incomplete, explain what is missing before summarising.
The skill improves only when someone saves and reviews the lesson. A successful chat does not automatically update the repository.

Keep raw observations separate from derived outputs. Record the dataset version, code revision, environment, seeds and exact command for each result. For literature work, retain the source location and supporting passage for each extracted claim.

General knowledge

Put stable, verified workflow rules in project instructions and skills.

Run-specific state

Keep commands, errors, decisions and pending work in a run log or handoff.

Store enough evidence for a colleague—or your future self—to check the result without the original chat.

Evaluate the whole research workflow

  • Choose several representative tasks: a dataset validation task, an experiment comparison and a source-grounded literature summary. Define acceptance checks before any model sees them.
  • Start each trial from the same commit, fixtures and task brief. Use separate working copies.
  • For a model comparison, hold the tool, permissions and available context constant. Record exact model names, date and reasoning settings.
  • Give each trial the same time or spend limit and correction policy. Repeat trials when practical; record failures too.
  • Review the diff and independently run the acceptance checks. A second model can propose findings, but reproduce each material finding.
  • Compare successful completion, regressions, human corrections, elapsed time and total cost. Do not select on tokens alone.

[13] · ADVANCED

Budget for a successful outcome

Scope

Ask for the smallest coherent change and focused output. Avoid dumping an entire repository into chat.

Measure

Track actual usage and retries on representative tasks. API token prices and product credits are different billing units.

Stop

Set a bounded trial. After repeated failure, inspect evidence and revise the approach.

Restart deliberately

Write a handoff before opening a fresh session. Include the commit, tests, unresolved work and next command.

A fresh chat can reduce irrelevant history, but it may also need to reload context. Caching, compaction and product billing affect the result; restarting is not guaranteed to cost less.

Handoff
- Goal and agreed scope
- Current commit / branch and uncommitted changes
- Relevant files and documentation versions
- Commands run, results and evidence paths
- Known failure or remaining uncertainty
- Next action and actions not yet authorised
Do not turn one observed credit charge into a universal price per edit. Recheck current plan limits and actual usage for the selected model.

[14] · ADVANCED

Choose one process for your next research session

  • Pick a repeated task that currently needs explanation or manual checking.
  • Capture one successful run, one failure and the criteria for completion.
  • Build one small tool with explicit inputs, useful errors and a known-answer fixture.
  • Write a skill that uses the tool and explains the decisions around it.
  • Trial it on a second example. Review the outputs and save only verified improvements.
The outcome is a reusable research method: code for the stable operations, a skill for the procedure, and evidence for the conclusions.
